# US-01: 추천 목적 카탈로그 정의

## 사용자 스토리

서비스 운영자로서 상황별 추천 목적을 한곳에서 관리하고 싶다. 그래야 홈, 랭킹, API가 같은 목적 이름과 key를 사용한다.

## 범위

- 목적 key를 정의한다.
- 목적별 한글 라벨을 정의한다.
- 목적별 짧은 설명을 정의한다.
- 최초 목적은 `date`, `conversation`, `photo`, `coffee`, `long_stay`로 제한한다.

## 제안 목적

| key | 라벨 | 설명 |
| --- | --- | --- |
| `date` | 데이트 | 분위기와 맛 만족도가 좋은 카페 |
| `conversation` | 대화 | 조용하고 편하게 이야기하기 좋은 카페 |
| `photo` | 사진 | 분위기와 비주얼 요소가 좋은 카페 |
| `coffee` | 커피맛 | 커피 맛 평가가 좋은 카페 |
| `long_stay` | 오래 앉기 | 좌석, 콘센트, 와이파이 사용성이 좋은 카페 |

## 프론트 영향

- 홈 섹션과 랭킹 화면이 같은 목적 정의를 사용해야 한다.
- 잘못된 key가 들어오면 기본 랭킹 또는 부부픽 랭킹으로 fallback한다.

## 백엔드/계약 영향

- `/api/cafemap/store-rankings`에 `purpose` query parameter를 추가할 수 있어야 한다.
- 지원하지 않는 purpose는 400을 반환하거나 기본 랭킹으로 fallback하는 정책을 정해야 한다.

## 역할별 할 일

### Frontend

- 목적 key, label, 설명을 한곳에서 읽을 수 있는 상수 또는 모델로 정리한다.
- 홈과 랭킹 화면이 같은 목적 정의를 사용하도록 연결한다.

### Backend

- `purpose` query parameter의 허용값을 정의한다.
- 지원하지 않는 값의 처리 정책을 정하고 구현한다.

### Designer

- 목적 한글 라벨과 짧은 설명 문구를 확정한다.
- 홈과 랭킹에서 같은 용어를 쓰도록 문구 기준을 맞춘다.

## 수용 기준

- 5개 목적의 key, 라벨, 설명이 문서화되어 있다.
- 프론트와 백엔드에서 같은 key를 사용한다.
- 새 목적을 추가할 때 수정해야 하는 위치가 명확하다.

## 검증 메모

- 목적 key가 홈 route, 랭킹 API, 화면 라벨에서 동일하게 쓰이는지 확인한다.
